# 项目设计文档

## 1. 项目定位

Flowchart Editor 是一个基于 Qt 6 的桌面流程图建模工具。项目的核心目标不是单纯“画几个图形”，而是建立一套可扩展的桌面建模架构，使其同时具备：

- 通用流程图编辑能力
- 可扩展组件系统
- 独立的连接线系统
- 可恢复、可持久化、可导出的文档体系
- 面向局域网直连场景的 P2P 协同能力

## 2. 设计目标

### 2.1 功能目标

- 支持常见流程图编辑操作
- 支持导出和文档保存
- 支持任意造型的自定义节点组件
- 支持连接线单独设计，不让箭头混入组件体系
- 支持欢迎页、最近文件、自动保存、恢复
- 支持基础协同编辑

### 2.2 架构目标

- 文档模型与视图解耦
- 节点定义注册化，而不是散落在各处的字符串分发
- 撤销重做走命令系统
- 运行数据可控，不污染系统目录
- 组件扩展采用统一协议，而不是增加越来越多的 C++ 子类

### 2.3 非目标

当前阶段未覆盖：

- OT / CRDT 级别的实时协同一致性
- 多对端协同房间
- NAT 穿透、信令服务器
- 自动避障路由
- 插件 ABI 稳定化
- 完整测试体系和 CI

## 3. 总体架构

项目按五层组织：

### 3.1 文档模型层

职责：

- 保存节点和连接线的纯数据模型
- 提供按 `id` 查询、克隆、遍历、插入、删除

核心对象：

- `DiagramItemModel`
- `NodeModel`
- `ConnectorModel`
- `DiagramDocument`

设计原则：

- 不依赖 `QGraphicsItem`
- 数据结构可以独立序列化
- 连接线端点通过 `EndpointRef` 引用节点与端口

### 3.2 会话层

职责：

- 维护当前编辑会话
- 协调文档模型和场景视图
- 统一处理命令、选择、撤销重做、复制粘贴、布局、校验、吸附

核心对象：

- `EditorSession`

设计原则：

- 所有编辑操作都以会话为中心
- UI 不直接操作底层文档数据
- 连接线、组件、属性修改统一走会话接口

### 3.3 渲染与交互层

职责：

- 把模型映射到 `QGraphicsScene`
- 处理鼠标交互、拖动、缩放、双击编辑文本、端口吸附、连线拖拽

核心对象：

- `CanvasView`
- `CanvasNodeItem`
- `CanvasConnectorItem`

设计原则：

- 视图对象只负责显示与交互，不保存长期业务状态
- 交互改动实时反馈到会话，再由会话回写模型

### 3.4 扩展与注册层

职责：

- 注册内置图元
- 加载用户自定义组件
- 统一图元绘制协议和端口协议

核心对象：

- `ShapeRegistry`
- `ShapeDefinition`
- `ComponentExtensionManager`
- `CustomComponentDialog`

设计原则：

- 新节点通过定义扩展，不通过继承爆炸扩展
- 自定义组件和内置组件走同一绘制通路

### 3.5 持久化与协同层

职责：

- 保存/加载文档
- 导出 Mermaid / PNG / SVG
- 最近文件和恢复快照
- P2P 快照协同

核心对象：

- `DocumentSerializer`
- `MermaidExporter`
- `SessionPersistence`
- `RuntimePaths`
- `PeerCollaborationManager`

## 4. 核心数据设计

## 4.1 图元模型

所有图元共享基础字段：

- `id`
- `typeId`
- `text`
- `zValue`
- `style`

其中 `style` 包含：

- 边框颜色
- 填充颜色
- 线宽
- 字体
- 粗体 / 斜体 / 下划线
- 旋转
- 缩放

### 节点模型

节点额外字段：

- `rect`
- `props`

`props` 用于存储节点类型特有的扩展属性。

### 连接线模型

连接线额外字段：

- `start`
- `end`
- `props`

`start` / `end` 使用 `EndpointRef`：

- `itemId`
- `portIndex`
- `position`

其含义是：

- 如果端点已附着到节点，则使用 `itemId + portIndex`
- 如果端点未附着，则使用自由坐标 `position`

## 4.2 组件定义协议

节点组件统一定义为 `ShapeDefinition`，核心字段包括：

- `typeId`
- `paletteLabel`
- `defaultSize`
- `defaultProps`
- `drawSpec`
- `portsSpec`
- `initializeStyle`

### 统一绘制协议 `drawSpec`

`drawSpec` 是一个命令数组，每条命令带 `op` 字段。绘制器根据命令生成 `QPainterPath`。

支持命令：

- `moveTo`
- `lineTo`
- `quadTo`
- `cubicTo`
- `rect`
- `roundedRect`
- `ellipse`
- `polygon`
- `arcMoveTo`
- `arcTo`
- `close`
- `parallelogram`

坐标默认使用归一化比例，映射到节点矩形。

### 端口协议 `portsSpec`

支持两类：

- 预设端口
  - `fourWay`
  - `twoVertical`
  - `twoHorizontal`
  - `none`
- 自定义端口点集
  - `points`

## 4.3 连接线属性协议

连接线特有属性放在 `props` 中，当前主要字段：

- `headStyle`
  - `classic`
  - `stealth`
  - `diamond`
  - `circle`
- `lineStyle`
  - `solid`
  - `dash`
  - `dot`
- `bendX`
  - 纵向折线中间列
- `bendY`
  - 横向折线中间行

设计上，连接线不属于组件，箭头样式也是连接线自己的协议，不从组件注册表加载。

## 5. 交互设计

## 5.1 欢迎页与工作区

程序启动后先进入欢迎页，而不是直接进入空画布。只有当用户：

- 新建文档
- 打开已有文档
- 从恢复快照恢复

才进入画布编辑状态。

这样做的目的：

- 明确文档生命周期
- 避免一启动就生成无意义空白文档
- 给最近文件和恢复入口留出独立空间

## 5.2 节点交互

节点支持：

- 拖动
- 8 向缩放手柄
- 双击文本编辑
- 属性面板同步编辑
- 旋转和缩放
- 端口吸附

交互原则：

- 鼠标拖动过程中走 `interactive` 更新
- 鼠标释放后统一提交为一个 undo 命令
- 节点几何变化后会刷新依赖它的连接线

## 5.3 连接线交互

连接线支持：

- 起点拖拽重连
- 终点拖拽重连
- 中间弯折点拖拽
- 自动路由
- 横向/纵向路由

交互原则：

- 连接线始终按正交流程线绘制
- 端点拖拽优先命中节点端口
- 手动弯折通过 `bendX` / `bendY` 持久化

## 5.4 属性编辑

属性面板负责编辑单选对象的公共属性：

- 文本
- 坐标
- 尺寸
- 旋转
- 缩放
- 填充透明度
- 线宽

顶部工具栏和二级连接线工具区负责更高频的样式操作：

- 字体
- 字号
- 字体粗斜下划线
- 边框颜色
- 填充颜色
- 连接线头型
- 连接线线型

## 6. 命令与撤销重做设计

项目基于 `QUndoStack`，命令分三类：

- `AddItemsCommand`
- `RemoveItemsCommand`
- `UpdateItemsCommand`

设计原则：

- 所有稳定的编辑结果都要落在命令栈中
- 拖动、缩放、弯折等连续交互，开始时记录 before，结束时统一提交 after
- 文档恢复和协同快照应用不走常规用户命令栈

## 7. 持久化设计

## 7.1 文档文件

文档使用版本化 JSON：

- 根字段 `version`
- 根字段 `items`

每个 item 保存：

- 基础字段
- 样式字段
- 节点几何或连接端点
- `props`

设计收益：

- 可读
- 易扩展
- 便于调试
- 便于外部工具转换

## 7.2 恢复快照

恢复快照单独保存：

- `sourceFile`
- `savedAt`
- `document`

保存位置为：

- `<exe-dir>/runtime-data/recovery.json`

## 7.3 最近文件

最近文件存放于本地 INI，不写入系统 AppData。

设计目的：

- 便携化
- 不污染系统目录
- 便于整包移动部署

## 8. 导出设计

项目支持三种导出方向：

- 图像导出
  - PNG
  - SVG
- 结构导出
  - Mermaid
- 组件包导出
  - 自定义组件 JSON

其中 Mermaid 导出走结构映射：

- 节点映射为 Mermaid 节点语法
- 已附着连接线映射为边
- 样式不会完全保留

## 9. 组件扩展设计

## 9.1 组件来源

组件来源分两类：

- 内置组件
- 用户组件目录中的扩展组件

用户组件目录：

- `<exe-dir>/runtime-data/components/`

## 9.2 组件管理面板

组件管理面板提供：

- 查看已安装组件
- 读取组件 JSON
- 直接编辑 JSON
- 保存修改
- 导出组件
- 删除组件
- 刷新注册表

## 9.3 自定义组件创建对话框

对话框支持：

- 组件 ID
- 显示名称
- 模板起步
- 默认宽高
- 线宽
- 边框色
- 填充色
- `drawSpec`
- `ports`

该设计兼顾了：

- 快速创建
- 低门槛编辑
- 对高级用户开放 JSON 协议

## 10. 协同设计

## 10.1 连接模型

协同采用 P2P 直连模式：

- 房主监听端口
- 成员输入房主 `IP:port` 连接

适用场景：

- 局域网
- 已配置端口映射的公网环境

## 10.2 消息模型

当前协议包含两类消息：

- `hello`
- `snapshot`

`hello` 用于交换：

- 协议版本
- peerId
- displayName

`snapshot` 用于交换：

- 文档快照
- revision
- reason

## 10.3 一致性策略

当前协同采用：

- 单房间单对端
- 全量文档快照同步
- `last write wins`

其优点是：

- 实现简单
- 容易调试
- 适合单机局域网演示

其缺点是：

- 粒度粗
- 易发生覆盖
- 不适合高频多方实时协同

## 11. 运行数据与部署设计

所有运行数据统一落在可执行文件目录旁：

```text
runtime-data/
```

这样做的设计价值：

- 便携发布更简单
- 不污染系统目录
- 用户可直接携带整个目录迁移
- 自定义组件和恢复数据天然与程序打包在一起

## 12. 关键权衡

### 12.1 为什么不让组件继承大量不同子类

因为目标是支持任意自定义组件。继续扩充 C++ 子类会导致：

- 类型爆炸
- 维护成本高
- UI、序列化、拖拽创建都被迫同步修改

统一 `drawSpec` 协议虽然牺牲了一些专用类的表达性，但换来了可扩展性。

### 12.2 为什么连接线不属于组件

因为连接线承担的是“关系”而不是“实体”：

- 它有端点、路由、弯折、箭头头型
- 它和节点的扩展诉求完全不同

把箭头塞进组件系统会让组件协议污染连接语义，因此单独设计更合理。

### 12.3 为什么运行数据落本地

因为项目目标之一是便携桌面工具。写到可执行文件旁边意味着：

- 不污染系统
- 更接近“绿色软件”
- 便于演示和打包
